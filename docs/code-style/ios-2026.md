# iOS development practice today, and what of it reaches an iOS 6 app

This chapter answers one question: of everything the iOS community currently agrees on, what
can actually be applied to 100,000 lines of Objective-C targeting iOS 6.0 on an iPhone 4S, and
what has to be discarded.

Most of it has to be discarded. That is not a complaint about the tooling; it is the working
condition. A chapter that recommends Swift concurrency to a project that cannot compile Swift
is worse than no chapter, because agents read this as law and will try to satisfy it.

What survives is a small set of ideas that are older than the languages people currently
express them in. Thin controllers, one direction of data flow, an explicit state value instead
of a scattering of booleans, parsing at the boundary, formatting away from layout. All of these
were expressible in Objective-C in 2010 and are expressible here.

Sources consulted for the "current practice" claims are listed at the end. Where practice is
contested, this chapter says so rather than pretending consensus.

---

## Part 0 — What is excluded, and why

Stated up front so no agent spends effort trying to apply it.

| Current practice | Why it does not reach us |
| --- | --- |
| Swift, Swift 6 strict concurrency, `async/await`, actors, `Sendable` | No Swift toolchain. armv7, iOS 6 SDK. Not negotiable, not partially adoptable. |
| SwiftUI, `@Observable`, the Observation framework | Requires Swift and iOS 17. |
| The Composable Architecture, Redux-style reducers with value-type state | Depends on value semantics, exhaustive `switch`, and structural equality that Objective-C does not have. The *direction* of data flow is borrowable (Rule 4); the machinery is not. |
| `Codable` / typed decoding | No Swift. See Part 2 for the Objective-C substitute. |
| Combine, `AsyncSequence`, `AsyncStream` | Swift-only. We have blocks and `NSNotificationCenter`, which is enough. |
| Swift Package Manager, modules, `@import` | The build is a hand-written Makefile against an iOS 6 SDK; TDLib is `dlopen`ed at runtime, not linked. See `src/TGClient.m`. |
| XCTest, snapshot testing, `swift-testing`, CI test gates | There is no test target and no simulator path. The only verification is a device build. Any rule phrased as "add a test" is unimplementable here. Rules in this chapter are therefore phrased as *checkable by reading a file or grepping*, never as *provable by a test*. |
| `UICollectionView` compositional layout, diffable data sources, `UIStackView`, Auto Layout | Post-iOS 6. Layout is manual `frame` arithmetic and will stay that way. |
| `UIAlertController`, `UIRefreshControl`, `NSURLSession`, `WKWebView` | Post-iOS 6. `UIAlertView`, custom pull-to-refresh, `NSURLConnection`, `UIWebView` are the local equivalents; the repo already has wrappers (`TGAlertView`, `TGActionSheet`). |
| Nullability annotations, lightweight generics, `NS_DESIGNATED_INITIALIZER` | The compiler here does not understand them. Do not add them, even "harmlessly" — they will not survive the build. |
| Dependency injection containers, protocol-oriented mocking | Justified mostly by testability. With no test target the cost is real and the benefit is not. `TGClient.shared` is the accepted seam; do not introduce a DI layer to replace it. |
| MVVM as a formal layer (a `…ViewModel` class per screen) | The *goal* — logic out of the view controller — is Rule 1 and is kept. The *ceremony* — a parallel class hierarchy plus a binding mechanism — costs memory and indirection we cannot pay on 40–60MB. Extract to plain functions, small model objects, and `TGClient` categories instead. |

One honest note on the surviving ideas: "make illegal states unrepresentable" is not uncontested
even where the type system supports it — the counter-argument is that over-modelled state
becomes hard to change and pushes complexity into conversion code. In a language with no sum
types, we get the weak form only: one state variable instead of five booleans (Rule 3). Do not
attempt the strong form by building class hierarchies per state.

## Part 1 — What the modern client does, and which parts we can steal

`/Users/alexanderhavrysh/Git/iOS/Telegram-iOS/submodules` solves the same problem, so it is worth
being specific about what transfers.

**Borrowable:**

1. **A hard boundary between "talking to Telegram" and "drawing Telegram."** `TelegramCore`
   owns the wire types; UI modules never see them raw. We have the same split already:
   `TGClient` plus 29 `TGClient+*` categories versus 31 view controllers. This chapter's job is
   mostly to defend that boundary, which is the single most valuable structural property this
   codebase currently has.
2. **A named state value per screen.** `ChatPresentationInterfaceState` is a struct with named
   sub-states (`ChatInputMode`, `ChatSearchResultsState`). We cannot have the struct or the
   enums-with-payload, but we can have `TGLoginStep`-style `NS_ENUM`s — the repo already does
   this in `TGLoginViewController.m`, `TGStickersViewController.m`, `TGChatEventsViewController.m`.
3. **Presentation data (colours, metrics, strings) passed in, not reached for.** We have
   `TGTheme` / `TGIcons`; keep using them rather than inlining colours.
4. **Feature-shaped file organisation.** They have one directory per feature; we have one
   `TGClient+Feature.{h,m}` pair per feature. Same idea, smaller.

**Not borrowable:**

- `AsyncDisplayKit` / node-based off-main-thread layout. Their answer to layout cost is a
  whole framework. Ours is Rule 7 (cache measured heights) and Rule 8 (no formatting in
  layout). Do not attempt to port node layout.
- `Postbox`. A transactional local database with views that push deltas. We have `TGClient`'s
  in-memory dictionaries and 40MB. Do not introduce a persistence layer.
- `SwiftSignalKit` signals with disposables and composition. Blocks with a single callback are
  the local equivalent. Do not write a signal library.
- Their module graph (hundreds of submodules). We have a flat `src/` of ~100 files and one
  Makefile; splitting further buys nothing without a module system.

## Part 2 — TDLib: the untyped-dictionary rules

TDLib is JSON in, JSON out. Every reply is an `NSDictionary` whose shape is described only by
its `"@type"` string, whose numbers may be `NSNumber` or missing, whose nested objects may be
absent, and which changes between TDLib versions without a compiler telling anyone. Thirty-one
screens consume these. This one fact generates most of the rules that matter here.

### Rule 1 — A view controller never reads `"@type"` and never indexes into a TDLib reply more than one level deep.

TDLib object shape is `TGClient`'s concern. A screen consumes a *flattened* dictionary with
flat keys it owns, the way `TGFlattenMessage` in `src/TGClient.m` already produces
(`"photoFileId"`, `"docName"`, `"extra"`, `"isService"`), or the way
`TGClient+ChatList` produces chat rows with `"id"`, `"title"`, `"text"`, `"unread"`.

Wrong (a view controller learning TDLib's schema):

```objc
NSString *type = message[@"content"][@"@type"];
if ([type isEqualToString:@"messagePhoto"]){
    NSNumber *fid = [message[@"content"][@"photo"][@"sizes"] lastObject][@"photo"][@"id"];
    [self loadThumb:fid];
}
```

Right (the shape is decided once, in the client layer):

```objc
NSNumber *fid = message[@"photoFileId"];
if ([fid isKindOfClass:NSNumber.class])
    [self loadThumb:fid];
```

If a screen needs a field the flattener does not expose, the fix is to add the field to the
flattener in `TGClient`/`TGClient+…`, not to reach through.

**How to check a file:** `grep -n '@"@type"' src/TGYourViewController.m` — a view controller
should return nothing. `grep -n '\]\[@"' src/TGYourViewController.m` — chained subscripts on a
TDLib dictionary are the other signature.

**Status: retrofit, but narrowly.** Only five view controllers violate it today
(`TGChatViewController`, `TGSearchViewController`, `TGMediaViewController`,
`TGEditProfileViewController`, `TGCountryPickerViewController`). That is a small, bounded job
and it is the highest-value retrofit in this chapter. Do **not** attempt a sweeping
re-flattening of every screen; the other twenty-six already comply.

### Rule 2 — Every value taken out of a TDLib dictionary is class-guarded before use, in the layer that first touches it.

`isKindOfClass:` is not defensive noise here; a missing key gives `nil` (usually survivable) but
a wrong-typed value gives an unrecognised-selector crash on a device with no debugger attached.
The codebase already does this heavily (`src/TGProfileViewController.m` has 137 guards,
`src/TGClient+Search.m` guards every extraction).

Use the per-file static accessor pattern that 19 files already use:

```objc
static NSDictionary *TGXDict(id v){ return [v isKindOfClass:NSDictionary.class] ? v : nil; }
static NSArray    *TGXArray(id v){ return [v isKindOfClass:NSArray.class]      ? v : nil; }
static NSString   *TGXString(id v){ return [v isKindOfClass:NSString.class]    ? v : nil; }
static NSNumber   *TGXNumber(id v){ return [v isKindOfClass:NSNumber.class]    ? v : nil; }
```

Wrong:

```objc
NSString *title = chat[@"title"];
cell.textLabel.text = [title stringByAppendingString:@" "];   // NSNull → crash
```

Right:

```objc
NSString *title = TGXString(chat[@"title"]);
cell.textLabel.text = title.length ? title : @"";
```

**How to check a file:** in any `.m` that reads TDLib replies, every `dict[@"key"]` whose result
is then messaged with something other than a universal selector must pass through a guard or an
`isKindOfClass:` test. A file that reads TDLib replies and contains zero `isKindOfClass:` is
almost certainly wrong.

**Status: new code — mandatory. Retrofit — only on crash sites and on files being edited
anyway.** Blanket-guarding 100,000 lines is thousands of mechanical edits with real diff risk
and no way to verify beyond one device build. Guard as you go.

### Rule 3 — Do not unify the guard helpers into a shared header.

This contradicts the usual instinct and is deliberate. There are currently ~40 near-identical
`TGxxDict` / `TGxxNumber` / `TGxxString` statics across 19 files. That duplication is roughly
150 lines total, all of it `static` and inlinable, and it costs nothing at runtime. Replacing
them with one shared header touches 19 files, renames symbols used hundreds of times, and can
only be validated by a full device build. The duplication is *correct*, it is just repeated.

**What to do instead:** in a new file, copy the four statics with a file-specific prefix, exactly
as `TGClient+SecretChats.m` (`TGScDict`) and `TGClient+Search.m` do. Naming convention: `TG` +
the file's two-to-three-letter tag + the class name.

**Status: new code only. Explicitly do not retrofit.**

### Rule 4 — Flattening happens exactly once per reply type, in `TGClient` or a `TGClient+` category, and the flattened key set is documented in the header.

`TGClient.h` already documents the chat-row key set in a comment above the `chats` property.
That comment is the contract; it is the closest thing this project has to a type.

Wrong: two screens each writing their own `messagePhoto` unpacking, drifting apart when TDLib
changes.

Right: `TGFlattenMessage` produces one dictionary; `TGChatViewController`,
`TGSearchViewController`, `TGSavedMessagesViewController` all consume the same keys.

**How to check:** for a new TDLib object type, grep the whole of `src/` for its `"@type"`
string. If it appears in more than one `.m`, either the second occurrence is in a view
controller (Rule 1 violation) or the same unpacking exists twice (this rule's violation).

**Status: new code. Retrofit only where a grep shows the *same* `"@type"` unpacked in two
places** — that is a real divergence bug waiting to happen, and there are only a handful.

### Rule 5 — Telegram ids travel as `int64_t` / `long long` from the dictionary to the last use.

32-bit target: `NSInteger` is 32 bits and `intValue` truncates. Chat ids, user ids, message ids
and supergroup ids are all 64-bit.

Wrong:

```objc
int chatId = [chat[@"id"] intValue];
```

Right:

```objc
int64_t chatId = [TGXNumber(chat[@"id"]) longLongValue];
```

Format with `%lld`, never `%ld` or `%d`. Box with `@(chatId)`.

Exceptions that are genuinely 32-bit and may stay `int`/`NSInteger`: `secret_chat_id`, folder
ids, unix `date`, durations, counts. `src/TGClient+SecretChats.m` casting to `int` is correct.

**How to check:** `grep -n 'intValue' src/File.m` and look at what the value is. Any hit on a
key named `id`, `chat_id`, `user_id`, `message_id`, `sender_id`, `supergroup_id`,
`from_chat_id`, `reply_to_message_id` is a bug.

**Status: retrofit — yes, and it is the second-highest-value retrofit here.** It is a
truncation bug, not a style issue, it is grep-findable, and each fix is local. Known live
example: `src/TGContactsViewController.m:1628` and `src/TGSavedMessagesTagsViewController.m:127`
class of usage should be audited under this rule.

### Rule 6 — All TDLib traffic goes through `TGClient` or a `TGClient+` category. A view controller never calls `-request:completion:`.

The screen asks a question in its own vocabulary (`canSendInChat:completion:`,
`membersOfChat:completion:`); the category translates it to JSON. This is already true in 96 of
100 files and is the property that makes the codebase survivable.

Wrong, inside a view controller:

```objc
[[TGClient shared] request:@{@"@type": @"getChat", @"chat_id": @(chatId)}
                completion:^(NSDictionary *r){ ... }];
```

Right:

```objc
[[TGClient shared] chatInfo:chatId completion:^(NSDictionary *chat){ ... }];
```

with the method living in the relevant `TGClient+…` category, and the completion receiving a
flattened dictionary, never the raw reply.

**How to check:** `grep -n 'shared\] request:' src/TGYour*ViewController.m` must be empty.

**Status: retrofit — yes, cheap.** Exactly four view controllers violate it today
(`TGCountryPickerViewController`, `TGEditProfileViewController`, `TGMediaViewController`,
`TGSearchViewController`), five call sites total.

### Rule 7 — A completion block always runs, exactly once, on the main queue, and always has a defined failure value.

TDLib can answer with `{"@type":"error"}`, or never answer at all. `TGClient` already handles the
second case with a 300-second deadline sweep and `failPendingRequests:`. The caller's obligation
is the first.

Wrong (block silently never fires, screen spins forever):

```objc
[[TGClient shared] request:req completion:^(NSDictionary *r){
    if ([r[@"@type"] isEqualToString:@"error"]) return;
    completion(TGXArray(r[@"members"]));
}];
```

Right:

```objc
[[TGClient shared] request:req completion:^(NSDictionary *r){
    NSArray *members = TGXArray(r[@"members"]);
    if (!members || [TGXString(r[@"@type"]) isEqualToString:@"error"]){
        if (completion) completion(@[]);
        return;
    }
    if (completion) completion([self flattenMembers:members]);
}];
```

The empty array, `nil`, or `0` is a *result*, not an absence of one. A screen must be able to
leave its loading state on every path.

**How to check:** for each `completion(` inside a `-request:completion:` block, confirm there is
no `return` path in the block that skips it. An early `return` before any `completion(` call is
the violation.

**Status: retrofit — yes, but scoped to the client layer only** (`TGClient*.m`, 30 files). Those
are the blocks whose failure strands a screen. Do not sweep view controllers for this.

### Rule 8 — Type checks on TDLib strings use a single `if`/`else if` chain or a dictionary lookup, never nested conditionals more than two deep.

`TGFlattenMessage` and `TGSearchTextForContent` are the reference shape: one flat chain over
`"@type"`, each branch small, one exit. This is readable, greppable and cheap. A nested tree of
`"@type"` tests is not.

**Status: new code only.** The existing chains already follow it.

## Part 3 — The general practices that survive translation

### Rule 9 — A view controller holds no logic that could be a free function over its inputs.

The modern phrasing is "thin controller / logic in the view model". The Objective-C form: if a
computation depends only on its arguments, it is a `static` C function at the top of the file
(or in a `TGClient+` category if other screens need it), not a method on the controller.

`TGChatViewController.m` gets this right for geometry (`TGDrawnSizeForImageSize`,
`TGImageDrawnAtPointSize`, `TGChatHexColour` are all file-scope statics) and it is why a
10,229-line file is navigable at all.

**How to check:** a method that never touches `self` except to read one ivar is a candidate. If
it never touches `self` at all, it is a violation.

**Status: new code. Retrofit only inside a file already being restructured for another reason.**

### Rule 10 — A screen's mode is one `NS_ENUM`, not a set of booleans, whenever two or more booleans are mutually exclusive.

The weak, achievable form of "make illegal states unrepresentable". `TGLoginViewController.m`
(`TGLoginStep`), `TGStickersViewController.m` (`TGStickerSuggestMode`) and
`TGChatEventsViewController.m` (`TGEventsFilterPage`) already do it.

Wrong (`TGStoriesViewController.m` has nine BOOL ivars; three of them —
`_dismissing`, `_holdPaused`, `_modalPaused` — plus `_onScreen` describe one playback mode with
combinations that cannot legally coexist):

```objc
BOOL _dismissing;
BOOL _holdPaused;
BOOL _modalPaused;
BOOL _onScreen;
```

Right:

```objc
typedef NS_ENUM(NSInteger, TGStoryPlayback) {
    TGStoryPlaybackIdle = 0,
    TGStoryPlaybackRunning,
    TGStoryPlaybackHeld,
    TGStoryPlaybackModal,
    TGStoryPlaybackDismissing
};
TGStoryPlayback _playback;
```

Booleans that are genuinely independent (`_loading`, `_exhausted` for a paging list;
`_searchFieldStyled` for a one-time setup) stay booleans. The test is: can I write down a
combination of these flags that must never occur? If yes, they are one enum.

**How to check:** `grep -c '^\s*BOOL _' src/File.m`. Four or more in one class warrants
reading them; then ask the mutual-exclusion question. Current counts:
`TGStoriesViewController` 9, `TGSearchViewController` 7.

**Status: retrofit — yes, for the two files above, and only those.** Each is one file, the enum
is local, and the transitions become greppable. Do not go looking for more; below four booleans
the change is not worth the diff.

### Rule 11 — State changes in one direction: event → mutate the state value → one `-reloadUI` (or `-reloadData`) pass. A UI callback never mutates another view directly.

The borrowable half of unidirectional data flow. There is no reducer and no framework; the
discipline is that view-updating code exists in exactly one method per screen, and everything
else sets state and calls it.

Wrong:

```objc
- (void)didTapMute {
    _muted = !_muted;
    _muteButton.selected = _muted;
    _header.subtitle = _muted ? @"muted" : @"";
    [_table reloadData];
}
```

Right:

```objc
- (void)didTapMute {
    _muted = !_muted;
    [self applyState];
}
- (void)applyState {
    _muteButton.selected = _muted;
    _header.subtitle = _muted ? @"muted" : @"";
    [_table reloadData];
}
```

The cost this pays for on an A5 is real: it makes it possible to see, in one method, how many
layout passes an event triggers.

**How to check:** count the methods in a `.m` that assign to a subview's properties. More than
one or two (plus `cellForRowAtIndexPath:` and `layoutSubviews`) is a violation.

**Status: new code and new screens.** Retrofitting this to `TGProfileViewController` (4,649
lines) or `TGChatViewController` (10,229) is a rewrite, not a refactor. Do not attempt it.

### Rule 12 — No formatting inside `-layoutSubviews`, `-cellForRowAtIndexPath:`, or a height calculation.

Formatting means `NSDateFormatter`, `NSNumberFormatter`, `stringWithFormat:`,
`sizeWithFont:` on freshly built strings, byte-count strings, and pluralisation. These run
per-frame or per-row on one 800MHz core.

Two sub-rules, both already partly honoured:

1. **Formatters are file-scope statics, created once.** `TGChatListViewController.m:2715` and
   `TGForwardPicker.m:29` do this correctly. `TGInviteLinksViewController.m:250` allocates an
   `NSDateFormatter` inline — allocation of a formatter is expensive enough to notice.
2. **The formatted string is computed when the data changes and stored on the model
   dictionary**, not recomputed while drawing.

Wrong:

```objc
- (UITableViewCell *)tableView:(UITableView *)tv cellForRowAtIndexPath:(NSIndexPath *)ip {
    NSDateFormatter *f = [[NSDateFormatter alloc] init];
    [f setDateFormat:@"HH:mm"];
    cell.dateLabel.text = [f stringFromDate:...];
```

Right: static formatter, or a `"timeText"` key put on the flattened row when the row is built.

**How to check:** `grep -n 'Formatter alloc' src/File.m` — every hit must be inside a
`static … dispatch_once`/`if (!x)` initialiser at file scope, never inside a layout or cell
method.

**Status: retrofit — yes, for `NSDateFormatter alloc` sites only.** Grep-findable, about twenty
sites, each a two-line local change, each a measurable win on a 4S.

### Rule 13 — A method takes at most four parameters; beyond that it takes a dictionary or a small model object.

Applies to new methods. Existing long signatures in `TGChatViewController.m` stay; renaming them
churns hundreds of call sites for no runtime benefit.

**How to check:** count the colons in the selector.

**Status: new code only.**

### Rule 14 — Anything added from an SDK newer than 6.1 is guarded, and the unguarded path is the one that works.

46 files already use `respondsToSelector:` guards, and `TGCapabilities` exists for this. The
pattern in `TGChatViewController.m` is the reference:

```objc
if (UIGraphicsBeginImageContextWithOptions != NULL)
    UIGraphicsBeginImageContextWithOptions(size, NO, 0.0f);
else
    UIGraphicsBeginImageContext(size);
```

For C functions test the symbol against `NULL`; for methods use `respondsToSelector:`; for
classes use `NSClassFromString`. Never `#available`, never a raw call to a post-6.1 selector.

**How to check:** any selector you cannot find in the iOS 6.1 headers must appear within a
guard in the same method.

**Status: retrofit — yes, when found.** Each unguarded post-6.1 call is a launch crash on the
target device, which outranks any style consideration.

### Rule 15 — Memory: no unbounded cache, no retained decoded image beyond what is on screen, one `@autoreleasepool` around any loop that builds temporaries.

40–60MB usable before the kernel kills the process without warning. `TGClient.m`'s receive loop
wraps each iteration in `@autoreleasepool` and caps in-flight main-queue work at 48 with a
semaphore — that is the local idiom.

Concretely: any `NSMutableDictionary` used as a cache needs an eviction rule or a
`UIApplicationDidReceiveMemoryWarningNotification` observer that empties it. Any loop over more
than ~50 TDLib objects that builds strings or images gets an `@autoreleasepool` inside the loop
body.

**How to check:** for each `NSMutableDictionary`/`NSMutableArray` ivar that only ever grows,
find the code that shrinks it. If there is none, it is a violation.

**Status: retrofit — yes, for caches keyed by message or file id.** Those are the ones that grow
without bound in a long chat session. Other retrofits under this rule: new code only.

## Applying this chapter

Order of work, highest value first:

1. Rule 5 — 64-bit id truncation. It is a correctness bug, grep-findable.
2. Rule 14 — unguarded post-6.1 API. Launch crashes.
3. Rule 6 — four view controllers calling `-request:` directly. Five call sites.
4. Rule 1 — five view controllers reading `"@type"`. Bounded, and it protects the boundary that
   makes everything else possible.
5. Rule 12 — inline `NSDateFormatter` allocation. ~20 sites, measurable on-device win.
6. Rule 7 — completion blocks with a skipping `return`, client layer only.
7. Rule 15 — unbounded caches keyed by message or file id.
8. Rule 10 — the two files with mutually exclusive boolean sets.

Everything else in this chapter applies to code written from now on. If a rule here cannot be
satisfied in this codebase, the rule is wrong and should be reported rather than worked around.
