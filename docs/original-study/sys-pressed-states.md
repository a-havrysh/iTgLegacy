# Pressed states in Telegram for iOS 1.1 (2014)

Scope: how the original expressed "this control is being touched". The three mechanisms are
(1) a second hand-drawn PNG per asset, selected by a naming suffix; (2) `highlightedTextColor`
on every label that sits over a highlight; (3) a `selectedBackgroundView` image on cells, with a
one-point overdraw so the pressed row eats the separator above it.

Paths below are relative to
`/Users/alexanderhavrysh/Git/iOS/telegram-original-sources/extracted/telegram_iphone.src`
unless stated otherwise. Our port lives in `/Users/alexanderhavrysh/Git/iOS/iTgLegacy/src`.

---

## 1. The rule: pressed is an asset, not an effect

Nothing in the original computes a pressed appearance. There is no alpha multiplier, no
`adjustsImageWhenHighlighted`, no tint. Every pressed state is a second PNG drawn by a designer
and shipped alongside the normal one. The suffix says which family it belongs to:

| Suffix | Count in `Telegraph/Telegraph/Resources` | Meaning |
|---|---|---|
| `_Highlighted` | 88 | the dominant convention: pressed twin of a normal asset |
| `_Pressed` | 31 | same meaning, used for chrome (nav bar, camera, input panel) |
| `_Selected` | 10 | pressed twin **and** sticky-state twin; see §5 and §7 |
| `_Active` | 5 | not a press state (recording/live indicators) |

Counted with `ls Telegraph/Telegraph/Resources | grep -c _Highlighted` etc. The suffix is not
semantic — `_Highlighted` and `_Pressed` are interchangeable and both feed
`UIControlStateHighlighted`; which one a control uses depends only on which designer cut the
asset. Compare `TelegraphKit/TelegraphKit/TGToolbarButton.m:17`
(`BackButton_Pressed.png`) with `TelegraphKit/TelegraphKit/TGMenuView.m:301`
(`MenuButtonLeft_Highlighted.png`) — identical mechanism, different suffix.

`UIButton`'s own dimming is switched **off** wherever a custom pressed asset exists:
`self.adjustsImageWhenDisabled = false; self.adjustsImageWhenHighlighted = false;`
(`TelegraphKit/TelegraphKit/TGToolbarButton.m:285-286`, and the same pair at
`Telegraph/Telegraph/TGContactCell.m:394-395`, `Telegraph/Telegraph/TGPhoneItemCell.m:189-190`,
`Telegraph/Telegraph/TGUserMenuItemCell.m:110-111`,
`TelegraphKit/TelegraphKit/TGWebController.m:217-218` and six more in that file). This is the
single most important rule of the system: **the system dim is always disabled, and a designed
asset always replaces it.** A control with no `_Highlighted` twin simply does not react.

The one runtime-generated exception: when a custom wallpaper forces monochrome message chrome,
the pressed variant of the inline upload-cancel button is generated by re-rendering the same
vector at `alphaFactor:1.4f` and cached to `Documents/assets/messageProgressCancel_Highlighted%x.png`
(`Telegraph/Telegraph/TGTelegraphConversationMessageAssetsSource.m:611-641`). Only here does the
original compute a highlight, and only because the base colour is unknown at build time.

## 2. Text: `highlightedTextColor` is always white, with two exceptions

61 call sites set `highlightedTextColor`; almost all of them are literally
`[UIColor whiteColor]` or `UIColorRGB(0xffffff)` — e.g.
`Telegraph/Telegraph/TGFlatActionCell.m:45`, `TGSwitchItemCell.m:41`,
`TGVariantMenuItemCell.m:29` and `:39`, `TGLabelMenuItemView.m:32` and `:42`,
`TGLoginCountryCell.m:25` and `:35`, `TGMainTabsController.m:79/89/99`.
`TelegraphKit/TelegraphKit/TGLayoutModel.m:56` does the same for generated labels.

The rule is: **the blue highlight plate is dark enough that every colour on it collapses to
white.** Blue link text (`0x0779d0`), grey subtitles (`0x888888`), green encrypted titles
(`0x229a0a`) all become `#ffffff` while pressed. There is no attempt to preserve hierarchy.

Two exceptions, both because the element keeps its own background:

- **Unread badge count.** `TelegraphKit/TelegraphKit/TGDialogListCell.m:422` sets
  `_unreadCountLabel.highlightedTextColor = UIColorRGB(0x2371c2)` — the badge itself inverts
  (blue plate → white plate, `DialogListUnreadBadge_Highlighted.png`,
  `Telegraph/Telegraph/TGInterfaceAssets.mm:242-247`), so the digits go blue, not white.
  The badge's text shadow is also cleared while pressed
  (`TGDialogListCell.m:421`, `highlightedShadowColor = clearColor`).
- **Nearby-user badge.** `Telegraph/Telegraph/TGAddContactsNearbyCell.m:97` uses
  `UIColorRGB(0x036ceb)` for the same reason.

Buttons that carry text through a `UIButton` use the state API rather than the label property,
with all three highlighted permutations spelled out:
`Telegraph/Telegraph/TGTokenView.m:58-62` sets white for `Highlighted`, `Selected`, and
`Highlighted|Selected`. Toolbar buttons deliberately do **not** change text colour — the label
is white in both states and only the plate swaps
(`TelegraphKit/TelegraphKit/TGToolbarButton.m:186` returns `whiteColor` unconditionally,
`:396-399` swaps only the background image).

### 2a. Propagating highlight into custom-drawn views

`UITableViewCell` propagates highlight by walking its subviews and calling `setHighlighted:` on
those that implement it (`UILabel`, `UIImageView`, `UIControl`). Views that draw text themselves
in `drawRect:` are invisible to that walk. The original's answer is a one-purpose shim:

`TelegraphKit/TelegraphKit/TGHighlightTriggerLabel.m` is a hidden, zero-size `UILabel` subclass
whose `setHighlighted:` forwards to a `targetViews` array (`:17-28`), optionally through
`advancedSetHighlighted:` when `advanced` is set. Two users:

- `TelegraphKit/TelegraphKit/TGDialogListCell.m:377-381` — trigger targets `_textView`
  (the `TGDialogListTextView` that draws title, preview, author and typing text).
- `Telegraph/Telegraph/TGContactCell.m:430-432` — trigger targets `_contactContentsView`.

The receiving view caches the flag and redraws:
`TGDialogListCell.m:175-182` (`setHighlighted:` → `setNeedsDisplay`), and its `drawRect:`
(`:184-297`) branches on `_highlighted` for **every** ink it lays down:
title `0x111111` → white, encrypted title `0x229a0a` → white, preview `_textColor` → white,
author name `0x345f8f` → white, typing text `actionTextColor` → white
(`:195, 247-282`). The group/secret-chat glyph is swapped for its `_Highlighted` twin **and
drawn with `kCGBlendModeCopy` instead of `kCGBlendModeNormal`** while highlighted
(`:226` and `:247`) — the highlighted glyph is white with soft edges, and normal blending over
blue would leave a halo, so it is copied straight into the context including its alpha.

## 3. Cells: `selectedBackgroundView` is a 2px-wide vertical gradient strip

Flat (ungrouped) lists set both a `backgroundView` and a `selectedBackgroundView`, each a plain
`UIImageView` holding a fixed-height strip that the cell stretches horizontally.

| Asset | pixel size (@2x) | point height | used by |
|---|---|---|---|
| `CellHighlighted88` | 2 × 88 | 44 | `TGFlatActionCell.m:34`, `TGBlockActionCell.m:35` |
| `CellHighlighted96` | 8 × 96 | 48 | `TGImagePickerGalleryCell.m:30`, `TGImageSearchQueryCell.m:22` |
| `CellHighlighted102` | 2 × **104** | 52 | `TGContactCell.m:303`, `TGAddContactsNearbyCell.m:43`, `TGDialogListSearchCell.m:54` |
| `DialogListCellHighlighted` | 4 × 146 | 73 | `TGDialogListController.mm:1138` |

Sampled with PIL from `Telegraph/Telegraph/Resources`. Three observations that only show up when
you open the files:

1. **`CellHighlighted102` is 104px, not 102.** The name records the design intent (51pt row,
   102px); the shipped art is one point taller so the row can be drawn at `y = -1` and still
   fill to its own bottom edge. `CellHighlighted88` and `CellHighlighted96` are exactly their
   nominal heights, so the same `-1` offset leaves them one pixel short at the bottom — an
   inconsistency the original lived with.
2. **The gradient is fixed-height, never stretched vertically.** They are installed with
   `initWithImage:` and no cap insets. Row height must match the asset, or the gradient
   compresses/clips. `DialogListCellHighlighted` is the exception: it is made stretchable
   *horizontally only* — `stretchableImageWithLeftCapWidth:1 topCapHeight:0`
   (`TGDialogListController.mm:1138`) — and its 73pt height is exactly
   `heightForRowAtIndexPath` for a conversation row (`TGDialogListController.mm:1123`).
3. **All four share one gradient.** Top hairline `#0085e5` (2px), then a jump to `#26a4f9` and a
   smooth ramp down to `#1477da` at the bottom, closed by a 2px `#005fbe`/`#0060bf` bottom
   hairline. `CellHighlighted96` is the odd one: `#098be9` top hairline, `#239bf3` → `#167bdd`
   ramp, `#0869c9` bottom — a slightly darker, less saturated cut of the same idea. Whether that
   was intentional or a re-export is not knowable from the source; treat 88/102/DialogList as
   the canon and 96 as a one-off.

### 3a. The `-1 / +1` overdraw and the z-order fix

A pressed row must cover the hairline separator *above* it, otherwise the blue plate looks like
it starts one pixel late. Both list cells do the same two things on every highlight/selection
transition:

```objc
selectedView.frame = CGRectMake(0, -1, selectedView.frame.size.width,
                                selectedView.frame.size.height + 1);
```
`TelegraphKit/TelegraphKit/TGDialogListCell.m:570-571` and `:576-579` (`adjustOrdering`),
mirrored in `Telegraph/Telegraph/TGContactCell.m:711-716` and `:731-736`.

And `adjustOrdering` (`TGDialogListCell.m:574-604`, `TGContactCell.m:784-...`) walks the table
view's subviews, finds the highest index occupied by a `UITableViewCell` or `UISearchBar`, and
`insertSubview:atIndex:` moves the pressed cell there. Without it, UIKit's arbitrary cell
z-order lets the *next* row's opaque background paint over the one-point overhang.

The whole dance is triggered from `setSelected:animated:` and `setHighlighted:animated:`.
Note a real bug in the original: `TGDialogListCell.m:566` guards the frame adjustment with
`if ((highlighted && !wasHighlighted) && (!highlighted && wasHighlighted))`, which is never
true. It is harmless only because `adjustOrdering` at `:561-564` performs the same frame fix
on the rising edge. `TGContactCell.m:727-740` writes the condition correctly
(`if (highlighted || wasHighlighted)`). Copy the contact-cell version.

### 3b. Grouped (inset) cells: a four-corner set under a different suffix

Settings/profile-style grouped tables do not use `CellHighlighted*`. They install an empty
`UIImageView` as `selectedBackgroundView` at cell creation
(`Telegraph/Telegraph/TGSettingsController.m:265-266`, `:285-286`) and then assign one of four
images per row position at layout time (`TGSettingsController.m:311-335`, and identically in
`TGNotificationSettingsController.m:524-548`, `TGProfileController.m:236-263`,
`TGPhoneLabelController.m:186`, `TGChatSettingsController.m:451`, `TGPrivacySettingsController.m:391`,
`TGTextFontController.m:152`, `TGPeopleNearbyController.m:553`, `TGCustomNotificationController.m:185`):

- `groupedCellSingleHighlighted`, `groupedCellTopHighlighted`, `groupedCellMiddleHighlighted`,
  `groupedCellBottomHighlighted` — `Telegraph/Telegraph/TGInterfaceAssets.mm:643-721`.

The backing files use the `_Selected` suffix, not `_Highlighted`:
`GroupedCellTop_Selected.png` (58×90 @2x), `GroupedCellMiddle_Selected.png` (58×90),
`GroupedCellBottom_Selected.png` (58×88), `GroupedCellSingle_Selected.png` (52×88).
Same blue ramp as the flat strips (`#239bf2` at top → `#167fe0`/`#0867bf` at bottom).

Cap insets, on iOS 5+: `UIEdgeInsetsMake(5, 13, 6, width - 13 - 1)` with
`UIImageResizingModeStretch` — a 5pt top cap, 6pt bottom cap, 13pt left cap and a 1pt stretchable
column (`TGInterfaceAssets.mm:650`, `:674`, `:718`). That preserves the rounded corner and the
inner 1px light edge while the middle stretches to any width and height.

Three exceptions worth knowing:

- **Bottom is deliberately not resizable.** `TGInterfaceAssets.mm:693` reads
  `if (false && [rawImage respondsToSelector:...])` — the modern path is dead code, and the
  bottom cell always falls through to
  `stretchableImageWithLeftCapWidth:(width/2) topCapHeight:1`. A vertical cap of 1 means the
  bottom cell's highlight *does* stretch vertically from row 1px downward, unlike top/middle/single.
  This is why a tall bottom grouped row still looks right while a tall top row would smear.
- The pre-iOS-5 fallbacks differ per asset (`height - 2` for top/middle, `height / 2` for single).
  Irrelevant to us — iOS 6.1.3 always takes the `resizableImageWithCapInsets:` branch.
- Rows with an interactive control instead of a tap target set
  `selectionStyle = UITableViewCellSelectionStyleNone` and get no highlight at all:
  switch rows (`TGSettingsController.m:288`, `TGNotificationSettingsController.m:458`,
  `TGProfileController.m:2529`), comment/footer rows (`TGNotificationSettingsController.m:501`),
  loading and error rows (`TGContactsController.mm:1619`, `TGAddContactsController.mm:494`).
  Grouped button rows (`TGProfileController.m:2455`, `:2499`) also opt out because the button
  inside them carries its own `_Highlighted` plate.

### 3c. The second, pale cell highlight — multi-selection lists

When a contact list is in multi-select mode the blue flash would collide with the checkmark's
meaning, so the original swaps the whole idiom
(`Telegraph/Telegraph/TGContactsController.mm:1410-1419`, `adjustCellForSelectionEnabled`):

- `selectionStyle` becomes `UITableViewCellSelectionStyleNone` (also for disabled cells), which
  suppresses the blue `selectedBackgroundView` entirely;
- `TGContactCell.m:742-782` instead lazily builds `_highlightedBackgroundView`, inserted at
  index 0 of the **contentView**: background `UIColorRGB(0xe9eff5)`, frame `(0, -1, w, h+1)`,
  with a 1pt top stripe and a 1pt bottom stripe both `UIColorRGB(0xd5dee5)` (`:748-758`).
- It is created once and then toggled with `.hidden` (`:769`, `:781`) — never removed, never
  animated. Commented-out code at `:763-767` and `:775-780` shows they considered also darkening
  the subtitle to `0x778698` and abandoned it.

So: **blue plate = "this row will navigate"; pale plate = "this row toggles a checkmark".**
That distinction is a designed rule, not an accident, and it is the single easiest thing to get
wrong when porting file-by-file.

### 3d. A genuine contradiction: opaque label backgrounds

`TGFlatActionCell.m:43` sets `_titleLabel.backgroundColor = [UIColor whiteColor]` (a scrolling
optimisation), while `TGBlockActionCell.m:57` — a visually identical cell built from the same
`Cell88`/`CellHighlighted88` pair — sets `clearColor`. With a white label background the pressed
flat-action row shows a white rectangle around its (now white) text on the blue plate. Also
`TGDialogListCell.m:388` sets `_textView.opaque = true` with a white `backgroundColor`, but that
view is fully custom-drawn and repaints its whole rect on highlight, so it is fine.
**Do not copy the white label background.** It is an artefact, and the correct reference is
`TGBlockActionCell`.

propagation handles it for free:

  (`MenuDisclosureIndicator.png` / `_Highlighted.png`), used at `TGFlatActionCell.m:50`,
  `TGBlockActionCell.m:66`, `TGImagePickerGalleryCell.m:54`.
- chat-list glyphs — `DialogListSent`, `DialogListRead`, `DialogListArrow`, `DialogListPending`,
  `DialogList_Muted`, `DialogListEncryptedChatIcon`, `DialogListGroupChatIcon`, all with
  `_Highlighted` twins (`TGDialogListCell.m:99, 119, 139, 222, 243, 1189, 1215`).
- action-row icons — `ListIconInvite`, `ListIconFriends`, `ListIconEncrypted`
  (`TGFlatActionCell.m:82-87`), `ListIconBlock` (`TGBlockActionCell.m:73`),

## 5. Message bubbles: press is "context selected", and the suffix lies

The chat bubble has no `UIControlState`. Its pressed appearance is a separate image view faded
in over the normal one, driven by `setIsContextSelected:animated:`
(`TelegraphKit/TelegraphKit/TGConversationMessageItemView.mm:717-806`).

Assets and their real meanings (`Telegraph/Telegraph/TGTelegraphConversationMessageAssetsSource.m`):

| Asset | Accessor | What it actually is |
|---|---|---|
| `Msg_In.png` | `…IncomingSingle` (`:650-653`) | normal, short bubble |
| `Msg_In_High.png` | `…IncomingDouble` (`:656-673`) | normal, **tall** (≥48pt) bubble — "High" = height, not highlight |
| `Msg_In_Selected.png` | `…IncomingHighlighted` (`:675-683`) | **pressed** short bubble |
| `Msg_In_High_Selected.png` | `…IncomingDoubleHighlighted` (`:697-714`) | pressed tall bubble |
| `Msg_In_Selected_Shadow.png` | `…IncomingHighlightedShadow` (`:686-694`) | drop shadow for the pressed bubble |

This naming trap is worth stating twice: **`_High` means tall; `_Selected` means pressed.**
Outgoing mirrors it at `:731-780`.

Colours (centre pixel, @2x): incoming `#fbfbfb` → pressed `#def0ff`; outgoing `#d3fbb1` →
pressed `#aef57c`. So the press is a *saturation* shift in the bubble's own hue, not a blue
overlay — the opposite philosophy from the list cells.

Cap insets, from `updateBackground:` (`TGConversationMessageItemView.mm:2366-2405`):
short bubbles use `stretchableImageWithLeftCapWidth:20 topCapHeight:15` incoming and `15/15`
outgoing (`:652`, `:678`); tall bubbles (`layout.size.height >= 48`) switch to explicit
stretch insets `UIEdgeInsetsMake(15, 23, 15, 40 - 23 - 1)` incoming and
`UIEdgeInsetsMake(15, 17, 15, 40 - 17 - 1)` outgoing. **The pressed view is configured with the
same rule as the normal one, in the same method** — so a bubble that crosses the 48pt threshold
never mismatches its highlight art.

Media messages have no bubble (`layout.hideBackground`). They get a stretchable overlay instead,
`MsgAttachmentHighlightedOverlay.png` with caps at half its width/height
(`TGConversationMessageItemView.mm:735-743`), inset inside the photo frame by
`y += 3`, `height -= 5.5`, `x += 3.5` outgoing / `+= 7.5` incoming, `width -= 11`
(`:754-759`) — i.e. it lines up with the artwork's rounded corners, not the layout box.

Timing (`:765-805`): switching **on** is always instantaneous (`alpha = 1` immediately, even
when `animated` is true — the animated branch only handles the off transition); switching
**off** is a 0.3s alpha fade, after which both the highlight view and its foreground overlay are
removed from the hierarchy. The shadow view is snapped, not faded (`:769`, `:800`).

Two triggers, and only two:

1. **Long-press context menu.** `TelegraphKit/TelegraphKit/TGConversationController.mm:7378`
   sets it true while building the Copy/Forward/Delete/Select menu, `:7419` clears it if the hit
   test failed, `:3971` and `:1509` clear it on dismiss. The bubble stays tinted for as long as
   the menu is up — it is the menu's anchor, not a touch-down flash.
2. **Jump to message** (reply tap, search result). `:5911-5916` sets
   `_currentlyHighlightedMid` and highlights the target with no animation, then
   `_fadeOutCurrentlyHighlightedMessage` (`:1496-1517`) disables table interaction, waits
   **0.2s**, and fades the highlight out over 0.3s. Cells recycled during the scroll re-apply the
   highlight from `_currentlyHighlightedMid` in `cellForRow` (`:3489-3490`, `:3710-3711`) so the
   flash survives dequeue.

## 6. Popover menu, action panel: neighbours react too

The copy/forward callout (`TelegraphKit/TelegraphKit/TGMenuView.m`) is built from three
horizontal slices per button plus top/bottom hairlines, each an image view with a
`_Highlighted` twin (`:58-68`, `:301-304`). `TGMenuButtonView.setHighlighted:` (`:74-92`)
fans the flag out to all seven slices and — crucially — ORs in `self.selected` (`:82`), with the
symmetric `setSelected:` at `:94-112`. The first and last buttons swap their outer slice for the
rounded `MenuButtonLeft_Highlighted` / `MenuButtonRight_Highlighted`, everything else uses the
centre slice (`:317-338`).

Then the interesting part: pressing a button changes something *outside* it.
`menuButtonHighlighted` (`:256-290`) finds which button is pressed, computes whether the
callout's arrow x-position falls inside that button's frame (with special handling for the first
and last button so an arrow past the edge still counts, `:269-278`), and highlights
`MenuArrowTop` / `MenuArrowBottom` accordingly. Press the button the arrow points at and the
arrow turns blue with it; press a different button and it stays grey.

The same neighbour-awareness governs the profile action panel:
`TelegraphKit/TelegraphKit/TGConversationActionsPanel.m:421-436` picks
`ActionMenuDivider_RightHighlighted` when the button on the divider's **left** is pressed,
`ActionMenuDivider_LeftHighlighted` when the one on the right is, and plain `ActionMenuDivider`
otherwise — so the 1px seam always belongs to the pressed side. Buttons themselves swap
`ActionMenuButtonLeft/Middle/Right_Highlighted` (`:176-188`).

## 7. Where "pressed" is not a press

Three shapes reuse the same machinery for sticky state, which is why `_Selected` and
`_Highlighted` appear interchangeably in the code:

- `UIControlStateSelected` is mapped to the *pressed* image everywhere, e.g.
  `TGToolbarButton.m:396-399` assigns `backgroundPressed` to `Highlighted`,
  `Highlighted|Selected` **and** `Selected`; `TGTokenView.m:58-62` does the same for text colour.
  A latched button therefore looks exactly like a held one.
- The action panel latches on tap: `actionButtonPressed` sets `_actionButton.selected = true`
  (`TGConversationActionsPanel.m:446`) so the button stays pressed while its sheet is up.
- `TGContactCheckButton.setHighlighted:` (`Telegraph/Telegraph/TGContactCell.m:170-176`) has no
  asset at all — it scales the checkmark to `0.8` and restores identity in `touchesCancelled:`
  / `touchesEnded:` when the touch left the bounds (`:178-198`). This is the *only* transform-based
  press feedback in the client, and there is no animation on it.

## 8. What happened afterwards

**twelve** (`/Users/alexanderhavrysh/Git/iOS/twelve`) kept the Objective-C lineage but replaced
the asset pair with a generic control,
`submodules/LegacyComponents/LegacyComponents/TGModernButton.m`. `modernHighlight` defaults to
true (`:26`) and `setHighlighted:` (`:146-216`) picks the first available of three strategies:
fade in a `_highlightImageView` over the button, fade in a `_highlightBackgroundView` filled with
`_highlightBackgroundColor`, or — the fallback with no art at all — drive `self.alpha` to
`0.4` (`:199`), multiplied by `0.5` when disabled. All three animate over **0.2s** when
`_animateHighlight` is set, and snap otherwise. That is the exact effect the 2013 client refused
to use, adopted as the default once the number of buttons made hand-cut twins uneconomic. Around
a dozen call sites opt in (`TGContentBubbleViewModel.m:210`, `TGStickerMessageViewModel.m:213`,
`TGPaymentReceiptController.m:139`, …).

**Telegram-iOS today** completes the move: highlights are theme colours, not assets.
`submodules/TelegramPresentationData/Sources/DefaultDayPresentationTheme.swift:486` defines
`itemHighlightedBackgroundColor: UIColor(rgb: 0xe5e5ea)` (day) — a neutral grey, not blue, since
iOS 7 abandoned the blue selection plate. Every list item owns a
`highlightedBackgroundNode` (`submodules/ItemListUI/Sources/Items/ItemListDisclosureItem.swift:282`)
whose colour comes from the theme (`:646`).

Two details survived thirteen years unchanged and are worth noting as validation of §3a:

- the overdraw: `highlightedBackgroundNode.frame = CGRect(origin: CGPoint(x: 0.0, y: -UIScreenPixel),
  size: CGSize(width: params.width, height: height + UIScreenPixel))` (`:888`) — literally the
  original's `(0, -1, w, h+1)` in screen-pixel units;
- the z-order concern, now expressed as `insertSubnode(_:aboveSubnode:)` against the bottom
  stripe / top stripe / background node in that order (`:929-943`), replacing `adjustOrdering`.

What changed is the timing: on it is instant, off is a **0.4s** alpha fade with removal on
completion (`:947-955`), where the original's cells had no fade at all. Do not import that — a
0.4s trail on a 4S list would read as lag, and the 2013 look is a hard on/off.

### 9.1 `CellHighlighted88.png` is missing from the bundle — flat action rows highlight 8pt too tall
`/Users/alexanderhavrysh/Git/iOS/iTgLegacy/images` contains `Cell88@2x.png` and
`CellHighlighted102@2x.png` but **no `CellHighlighted88@2x.png`**

Fix: copy `Telegraph/Telegraph/Resources/CellHighlighted88@2x.png` (2×88) into `images/`, and
delete the `?:` fallback so a future miss fails visibly rather than silently mis-sizing.

### 9.2 Grouped settings cells have no highlight art at all
`grep -rn "GroupedCell.*_Selected" src/` returns nothing, and `src/TGTheme.m:423-427`
(`styleCell:`) substitutes a flat `UIView` coloured `TG_DARK_EDGE` or `bubbleThersColour`, with
the comment "A selection flash of white would be worse than none." That is a reasonable
stopgap but it is not the original: settings rows should carry
`groupedCellTop/Middle/Bottom/SingleHighlighted` with cap insets
`UIEdgeInsetsMake(5, 13, 6, w - 13 - 1)` (top/middle/single) and
`stretchableImageWithLeftCapWidth:w/2 topCapHeight:1` for bottom — original
`Telegraph/Telegraph/TGInterfaceAssets.mm:643-721`, assignment pattern
`Telegraph/Telegraph/TGSettingsController.m:265-266` and `:311-335`.
Note `styleCell:` also does not clear `selectionStyle` for switch rows; the original does
(`TGSettingsController.m:288`).

### 9.3 Multi-select contact rows flash blue instead of pale
`src/TGContactsViewController.m:234-236` installs `CellHighlighted102` unconditionally, and no
file in `src/` contains `0xe9eff5` or `0xd5dee5`. In the original, entering selection mode sets
`selectionStyle = UITableViewCellSelectionStyleNone` and swaps in a pale
`0xe9eff5` background with 1pt `0xd5dee5` stripes top and bottom
(`Telegraph/Telegraph/TGContactsController.mm:1410-1419`, `Telegraph/Telegraph/TGContactCell.m:742-782`).
The same applies to `src/TGForwardPicker.m:122,158-163` and `src/TGGroupMembersViewController.m:153-157`,
which are selection lists using the navigation-blue plate. Fix all three together: they are the
same rule.

### 9.4 Chat-list cell: no `-1 / +1` overdraw, no z-order fix
`src/TGChatListViewController.m:379-388` (`buildPlates`) installs the stretched
`DialogListCellHighlighted` correctly (cap 1/0, matching `TGDialogListController.mm:1138`) but
`setHighlighted:animated:` / `setSelected:animated:` (`:582-595`) only touch the badge shadow and
the date label. They never move the selected view to `(0, -1, w, h+1)` and never reorder the cell
above its neighbours. Original: `TelegraphKit/TelegraphKit/TGDialogListCell.m:555-604`.
Symptom with real data: a one-pixel grey line across the top of every pressed conversation row,
and occasionally a clipped bottom edge when the row below happens to be later in the subview
order. `src/TGContactsViewController.m:189-197` and `src/TGSearchViewController.m:263-268`
already do the frame half correctly (in `layoutSubviews`), so copy that and add the ordering walk.

### 9.5 Chat-list group/mute glyphs never highlight
`src/TGChatListViewController.m:370-372` builds `self.groupIcon` with
`initWithImage:` only, while the arrow immediately below (`:374-376`) correctly uses
`initWithImage:highlightedImage:`. The `_Highlighted` twin exists in the original for both the
group and the secret-chat glyph (`TelegraphKit/TelegraphKit/TGDialogListCell.m:222`, `:243`) and
for the mute icon (`:1215`). Result: pressing a group conversation leaves a blue-on-blue glyph.
Fix by passing `DialogListGroupChatIcon_Highlighted.png` (and the encrypted/mute equivalents).

### 9.6 Bubbles: `_Selected` art is bound to the wrong state
`src/TGChatViewController.m:7971-7977` appends `_Selected` when `drawingSelectedRow` is set, and
`drawingSelectedRow` is assigned at `:8526-8528` purely from multi-select checkbox state
(`self.selecting && [self.selectedIds containsObject:...]`). In the original the tinted bubble is
`isContextSelected` and has exactly two triggers — the long-press menu anchor
(`TGConversationController.mm:7378`) and the jump-to-message flash (`:5911-5916`) — while
multi-select mode shows a checkmark and leaves the bubble art alone
(`TGConversationMessageItemView.mm:717-806` is never called from the editing path).
Concretely:
- `src/TGChatViewController.m:5853-5865` (`messageHeld:`) opens the menu without tinting the
  bubble. It should set the held row's bubble to `Msg_*_Selected` on the way in and clear it
  when the menu closes.
- `src/TGChatViewController.m:4066-4081` (`scrollToMessageId:`) flashes
  `cell.contentView.alpha` 0.3 → 1.0 over 0.6s. The original never fades the content: it
  swaps the bubble to the pressed art instantly, holds **0.2s** with table interaction disabled,
  then fades the highlight layer out over **0.3s** (`TGConversationController.mm:1496-1517`).
  It also re-applies the highlight to recycled cells during the scroll (`:3489-3490`), which our
  version cannot do because it looks the cell up once, before the scroll animation finishes —
  so on a long jump the flash is frequently invisible.
- Whether to keep the current behaviour of tinting checked rows in selection mode is a product
  call; if kept, it should be documented as a deliberate divergence, because the original used
  the checkmark alone.

### 9.7 Landscape nav-bar plates are unset
`src/TGTheme.m:493-501` sets `BackButton` / `BackButton_Pressed` for
`UIBarMetricsDefault` only, with cap 15 — correct, matching
`TelegraphKit/TelegraphKit/TGToolbarButton.m:17`. The original also has a landscape pair
(`BackButton_Landscape_Pressed.png`, `TGToolbarButton.m:33`; likewise
`HeaderButton_Landscape_Pressed.png` at `:65`), which we neither ship in `images/` nor register
for `UIBarMetricsLandscapePhone`. In landscape the 30pt portrait plate is squeezed into the
25pt bar (`TGToolbarButton.m:513`). Low priority, but it is a real gap.

### What our port already gets right (no action)

## 10. Open questions

- `CellHighlighted96` uses a visibly different blue ramp from the other three strips. No source
  comment explains it, and no code compensates. Deliberate or a stale export is unknowable from
  what we have.
- `CellHighlighted102@2x.png` is 104px while the name says 102, and the sibling assets are not
  similarly padded. I read this as "only the 51/52pt row was fixed up for the `-1` offset", but
  the source never states it.
- `TGDialogListCell.m:566`'s always-false condition — dead code or an intended guard that was
  broken during a refactor? `adjustOrdering` masks it, so the difference is unobservable at
  runtime; `TGContactCell.m:732` has the correct form.
- Whether the original ever intended the chat bubble tint to appear in multi-select editing mode.
  `setEditing:` and `setIsContextSelected:` are entirely separate paths with no shared state, so
  the evidence says no, but the shared `_Selected` asset naming leaves room for doubt.
- Only `@2x` variants of the highlight strips exist in the shipped Resources folder. On a
  non-retina device `imageNamed:@"CellHighlighted88.png"` would find nothing. This is moot for us
  (4S is retina) but means the 2013 client's non-retina cells presumably fell back to the system
  blue selection — unverifiable from source alone.
